# Front-end (entrega final) — Plano de implementação

> **Para quem executa:** SUB-SKILL OBRIGATÓRIA: use superpowers:subagent-driven-development (recomendado) ou superpowers:executing-plans para implementar este plano tarefa por tarefa. Os passos usam caixas (`- [ ]`) para acompanhar.

**Objetivo:** a entrega final de 17/11: as telas web do admin e o app da equipe servidos pelo Flask, com todos os dados por `fetch`, e as rotas da API que essas telas pedem.

**Arquitetura:** abordagem A da spec. O Flask entrega páginas Jinja sem dados (`frontend/paginas`) e os estáticos (`frontend/estaticos`); cada tela é um módulo ES nativo que lê a URL, busca a API e monta o HTML com o template `html`. A API ganha as leituras que juntam dados e as escritas que faltavam (editar, cancelar, desativar, mudar o estado), nas mesmas três camadas da Etapa 2.

**Pilha:** Flask 3 + Jinja; HTML, CSS (`@layer`) e JavaScript do navegador, sem framework e sem compilação; GSAP 3.13 servido localmente; `unittest` com o banco de verdade; `node --test` (Node 24).

**Spec:** `docs/superpowers/specs/2026-11-08-front-end-design.md`. Junto com ela: `DESIGN.md` v0.4 (Apêndice B), `design/telas/web-admin.md`, `design/componentes/parte-3-lote-b.md` (lote B), `design/componentes/parte-1-regras-e-inventario.md` e a spec da API (`docs/superpowers/specs/2026-11-08-api-etapa-2-design.md`).

## Decisões deste plano (para a revisão de vocês)

1. As ações têm rota própria com `POST` (`/cancelar`, `/desativar`, `/reativar`, `/estado`, `/desfazer`, `/senha`), em vez de `PATCH` no status: cada uma tem regra própria e fica clara no teste.
2. `PATCH` recebe o formulário inteiro, com os mesmos campos do cadastro; o que falta vira vazio.
3. O conflito na hora (R1) é conferido no navegador, com as reservas e os bloqueios que o Seletor de datas já busca; o servidor continua recusando com 409.
4. Sessão expirada segue a spec do front (§8): o aviso leva para `/entrar?volta=…`. O diálogo com e-mail e senha da §3 de `web-admin.md` fica para depois; o que estava num formulário aberto se perde.
5. Receita do mês: o valor de cada reserva dividido pelas noites que caem no mês (de 30/10 a 3/11, contam 2 das 4 noites em novembro). Ocupação: noites ocupadas ÷ (imóveis ativos × dias do mês). Diária média: receita ÷ noites ocupadas. Reserva cancelada não conta.
6. O menu do admin oferece só as passagens que o domínio aceita (R5): pendente → em andamento ou concluída; em andamento → concluída; concluída → pendente (reabrir). Desfazer vale para começar e concluir (decisão 5 do lote B); reabrir não se desfaz.
7. A mesma rota de estado serve o admin e a equipe. A pessoa da equipe só muda as próprias tarefas e só um passo para a frente: pendente → em andamento → concluída.
8. Mudar a função de quem tem tarefas pendentes da função antiga dá 409; quem administra passa as tarefas antes.
9. As gavetas abrem de várias telas (Agenda, "Hoje", detalhe do imóvel), então moram em `js/gavetas/`, uma por assunto, fora de `js/telas/`.
10. `frontend/package.json` só com `{"type": "module", "private": true}`, para o Node ler os módulos como o navegador; sem dependências.
11. A Task 13 espera a seção de telas do app da equipe (`design/telas/app-equipe.md`) aprovada. Escrevo essa seção logo depois deste plano.
12. A escolha "Efeitos visuais" do menu da conta fica fora, como diz a spec (§1): o menu tem nome, e-mail e Sair.
